Fixed: all three now call `legacyMainSiteContextResolver.requireMain()`; every `ShipmentRepository` list/paged/count query (`findAllWithAssociationsList`, `findByStatusWithAssociationsList`, `findByStatusPaged`, `findByStatusAndSearch`, the ACTIVE/AWAITING_RECEIPT/PARTIAL/COMPLETED/FAILED page+count pairs, `findByItemsContainingProduct`) now takes `siteId` and filters on `s.site.id`. New tests: `ShipmentControllerSecurityTest.ReadOnlyEndpointMembershipTests` (3 tests — an authenticated user with no MAIN membership gets 403 from all three routes).
- **Finding 2 (High) — cross-site stock write via unscoped location lookup.** `addToInventory` looked up the receive allocation's `locationId` with a bare `locationRepository.findById`, so a shipment authorized for site A could add real stock at a location belonging to site B (the stock movement itself would have shown B's real site via `location.getStorageLocation().getSite()`, but the allocation record would have said A — inconsistent audit trail on top of the isolation break). Fixed: `addToInventory` now takes `siteId` and uses `locationRepository.findByIdAndSite_Id(locationId, siteId)`, rejecting a foreign-site location before any write. New test: `ShipmentServiceCrossSiteLocationIT` (1 test — receiving against another site's location throws `LocationNotFoundException` and writes nothing).
- **Finding 3 (Medium) — backfill could split one shipment across sites.** V70 originally derived each `shipment_item`/`shipment_item_allocation`'s site independently from its own location, so a shipment could end up with items attributed to different sites than itself or each other — contradicting the one-shipment-one-site invariant `ShipmentService` already enforces for every new row. Fixed: items/allocations now simply inherit their parent's (already-resolved) site. `ShipmentSiteBackfillIT`'s two divergent-location tests were rewritten to assert inheritance instead of independent resolution (`everyItemInheritsTheParentShipmentsSiteEvenWhenItsOwnLocationDiffers`, `everyAllocationInheritsItsParentItemsSiteEvenWhenItsOwnLocationDiffers`).

### Review-finding fixes, round 2 (2026-09-23, external review of the round-1 fixes)

- **Finding 1 (High) — undo could still debit another site's stock.** Round 1 fixed the *receive* path (`addToInventory`) but not *undo*: `removeFromInventory` looked up inventory via the unscoped `InventoryOperations.findInventory(locationId, productId)` two-arg overload. Since receive is now guarded, this could no longer be triggered by a fresh request through the normal flow — but a legacy allocation row (site_id inherited from its shipment by V70, `locationId` left exactly as it was before this migration) could still have a `locationId` belonging to a different, real site than its own `site_id`. Undoing such a shipment would reduce that other site's actual stock. Fixed: `removeFromInventory` now takes `siteId` and calls the existing site-scoped `InventoryOperations.findInventory(siteId, locationId, productId)` overload, which returns empty (→ `InsufficientInventoryException`) for a foreign-site location instead of the real row. New test: `ShipmentServiceCrossSiteLocationIT.undoRejectsWhenAnAllocationsRecordedLocationBelongsToAnotherSite` — receives legitimately at a MAIN location, then directly corrupts the persisted allocation's `locationId` to a foreign site (reproducing the legacy shape without going through any now-guarded service method), then asserts undo is rejected and the real MAIN stock is untouched.
- **Finding 2 (Medium) — location references still unvalidated at create/update, and disclosed in mapper output.** Two related gaps: (a) `createShipment`/`updateShipment` stored a request-supplied `destinationLocationId` with no site check, so a shipment item could permanently carry a foreign-site location reference from the moment it's created, not just as a migration artifact; (b) `ShipmentMapperDecorator.batchFetchLocationCodes` looked up every allocation's location via an unscoped `locationRepository.findAllById`, so a foreign-site location's real `locationCode` could be returned in a shipment's JSON response — a live cross-tenant information disclosure, not just an internal write-path bug. Fixed both: a new `requireSameSiteLocation(siteId, locationId)` helper rejects a foreign-site `destinationLocationId` at create/update time (no-op for null); `batchFetchLocationCodes` now takes `siteId` and filters to locations belonging to it, threaded through both `ShipmentMapperDecorator` public methods and all 10 `ShipmentController` call sites. New tests: `ShipmentServiceCrossSiteLocationIT.createShipmentRejectsAForeignSiteDestinationLocation`; `ShipmentMapperDecoratorTest.doesNotDiscloseAForeignSiteLocationsCode` (a foreign-site allocation's code renders as `"NA"`, never its real value).

### Review-finding fixes, round 3 (2026-09-23, external review of the round-2 fixes)

- **Finding 1 (Medium) — response still exposed foreign location ids.** Round 2 masked a foreign-site allocation's `locationCode` (replaced with `"NA"`) but left `locationId` itself in the DTO untouched, and never looked at the item-level `destinationLocationId` at all (never added to `collectLocationIds`, so it was never even considered). Fixed: `enrichAllocationsWithCodes` now nulls `allocation.locationId` whenever its code isn't resolved, and nulls `item.destinationLocationId` whenever it isn't in the site-scoped `locationCodes` map; `collectLocationIds` now also collects each item's `destinationLocationId`. The fetch is also now site-scoped in the query itself — a new `LocationRepository.findByIdInAndSite_Id` bulk method replaces the fetch-then-filter `findAllById` — so a foreign-site row is never materialized in the first place, not just excluded afterward. Updated test: `ShipmentMapperDecoratorTest.doesNotDiscloseAForeignSiteLocationsCode` now also asserts the foreign allocation's `locationId` is null (own-site `locationId` still returned). New test: `ShipmentMapperDecoratorTest.masksAForeignSiteDestinationLocationIdOnTheItemItself`.
- **Finding 2 (Medium) — webhook tracking-code fallback could select the wrong site's shipment.** `EasyPostWebhookService.findShipmentForTracker`'s fallback (used when the tracker id from the payload doesn't match any shipment) picked the *most recent* shipment with a matching `tracking_id` via `findFirstByTrackingIdOrderByCreatedAtDesc` — that column carries no uniqueness constraint, so two shipments (possibly at two different sites) can share a tracking code, and the "most recent wins" tiebreak could silently attach a real carrier-status update to the wrong site's shipment. Fixed: a new `ShipmentRepository.findByTrackingId` (list-returning) replaces the fallback lookup; the match is only accepted when it names *exactly one* shipment, and two-or-more matches are logged (`"Tracking code {} matches {} shipments; skipping ambiguous carrier-status update"`) and treated the same as no match. New test: `EasyPostWebhookServiceTest.ambiguousTrackingCodeMatchIsNotGuessedAt` (two shipments share a tracking code; neither is saved, and the idempotency record's `site` stays null).

### Structured location-id audit, round 4 (2026-09-23, external review with an explicit sweep for the sibling-instance pattern named at the end of round 3)

### T-2 — Site resolution design

- Normal (non-webhook) routes: reuse the existing generic `/api/v1/sites/{siteId}/**` mechanism used by every already-migrated module (e.g. `inventory.api.SiteInventoryMutationController`) — `identity.infrastructure.SiteAccessAuthorizationFilter` resolves and authorizes the path's `{siteId}` before the controller runs, via `identity.application.AuthorizedSiteContextFactory`, and the handler reads `shared.web.AuthorizedSiteContextHolder.require()`. No new authorization mechanism is needed for shipments; T-5's v1 routes just need to live under that path and read the held context, matching every other migrated module.
- Webhook route (`POST /api/webhooks/easypost`, unauthenticated server-to-server call from EasyPost, no `{siteId}` in the URL and no user principal): site cannot come from the path or a JWT. `EasyPostWebhookService.processTrackerEvent` already resolves the target `Shipment` row server-side (via `findByEasypostTrackerId`, falling back to `findFirstByTrackingIdOrderByCreatedAtDesc`) before doing anything else — T-4 wires that resolved `Shipment.getSiteId()` as the event's site for the realtime broadcast and stores it on the `WebhookEvent` audit row. The provider payload (`EasyPostWebhookPayload`/`EasyPostTrackerResult`) is never read for a site value at any point — there is no such field to read. This satisfies AC-2's "webhook mutation resolves an authorized or server-derived site before entity lookup" for the mutation itself (the `Shipment.setCarrierStatus(...)`/`shipmentRepository.save(...)` at line ~176) since the site is derived from the same row the lookup already found, not supplied by the caller.
- Idempotency recording (`WebhookEvent.save(...)` at line ~109) happens before the tracker event is routed/resolved, so that row's `site_id` cannot be filled at insert time for every event — only after `processTrackerEvent` resolves a `Shipment` does a site become knowable. T-4 will update the `WebhookEvent` row's `site_id` after resolution succeeds (best-effort second write in the same transaction), leaving it NULL for event types that never reach `processTrackerEvent` or for a tracker/tracking-code miss. This is why `webhook_events.site_id` stays nullable per V69/V70's migration comments rather than being constrained later like the other three tables.
- Decision (open risk from T-1, resolved): do NOT reject/park a webhook event when no matching `Shipment` is found. Current behavior already logs a warning and returns without mutating anything (`shipmentOpt.isEmpty()` branch, line ~142); there is no stock/status mutation to protect in that path, so there's nothing to authorize against and no site to derive. Rejecting would just turn an already-safe no-op into a retried/dead-lettered EasyPost event for no safety benefit.
